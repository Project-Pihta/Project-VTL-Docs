### Описание

Каждый модуль в `VTL` имеет свой заголовочный файл `module.vtl`, данный файл описывает всю минимально-необходимую информацию для дальнейшего запуска и/или сборки модуля. В число такой информации входят:
*Минимальные обязательные:*
- **Имя модуля** - полное системное (и визуальное) наименование модуля. Имя модуля может быть написано строчными латинскими буквами и цифрами, допускается дефис, но должно начинаться исключительно с буквы.
- **Версия модуля** - полная системная (и визуальная) версия модуля. Допускаются версии форматов `X.Y.Z` / `X.Y.Z-postfix`, в которых:
	- `X` - версия поколения модуля.
	- `Y` - версия добавлений / исправлений ломающая обратную совместимость.
	- `Z` - версия добавлений / исправлений не ломающая обратную совместимость.
*Зависимости и зависимые:*
- **Родительские модули** - список модулей по которому модуль определяет какие модули являются его родительскими модулями и каким модулям он приходится дочерним модулем.
- **Дочерние модули** - список модулей или правил (*regex*) по которому модуль позволяет определять какие модули могут быть его дочерними модулями. Для каждого модуля или правила возможно определять разрешение дочернего модуля на применение примесей к родительскому (по умолчанию примеси *разрешены*).
- **Зависимости** - список зависимостей модуля которые необходимы для его сборки и/или работы. Каждая зависимость в списке имеет такие параметры как:
	- **Имя зависимости** - имя модуля зависимости.
	- **Версия** - версия или допустимый диапазон версий. Допускаются обозначения формата *SEMVER*.
	- **Разрешение примесей** - параметр индивидуального разрешения или запрета на применение примесей зависимостью относительно модуля. Имеет высший приоритет относительно глобального разрешения зависимостей. По умолчанию *разрешено*.
*Примеси:*
- **Определение примесей** - параметр указывающий на то, что модуль определяет и может применять примеси относительно других модулей.  По умолчанию *запрещено*.
- **Разрешение примесей** - параметр глобального разрешения или запрета на применение примесей к модулю относительно всех сторонних, либо конкретных модулей. По умолчанию *разрешено*.
*Исходный код и ресурсы:*
- **Файлы исходного кода** - путь до каждого файла исходного кода и/или папки с его наличием. Пути должны обозначаться исключительно относительно (*и глубже*) директории расположения заголовочного файла модуля, допускается оператор звёздочка (`*`) для обозначения перебора директорий / файлов с исходным кодом.
- **Файлы ресурсов** - путь до каждого файла ресурса и/или папки с его наличием. Пути обозначаются аналогично путям с исходным кодом.

#### Примеры


```clojure
(module "vtl/module"
	; Минимальные обязательные
	; - Имя
	(name "example")
	; - Версия
	(version "1.0.0")
	
	; Зависимости и зависимые
	; - Родительские модули
	(parents [ "other/core" ])
	; - Дочерние модули
	(childs [
		; -- Дочерний модуль
		(module "example/extension-child"
			; --- Разрешение примесей
			(allow-mixin true)
		; -- Правило дочерних модулей
		(rule "example\/child\-[a-zA-Z]+"
			; --- Разрешение примесей
			(allow-mixin false)))
	])
	; - Зависимости
	(dependencies [
		; -- Зависимость в одну строку
		"vtl/core@1.0.0"
		; -- Зависимость в виде инструкции
		(module "vtl/io@1.0.*"
			; --- Разрешение примесей
			(allow-mixin true)
		; -- Зависимость в виде инструкции
		(module
			; --- Имя
			(name "vtl/utils")
			; --- Версия
			(version "~1.0.0")
			; --- Разрешение примесей
			(allow-mixin false))
	])
	; Примеси
	; - Определение примесей
	(allow-mixin-define true)
	; - Применение примесей
	(allow-mixin-apply false)
	; Исходный код и ресурсы
	; - Исходный код
	(sources ["source/*.vtl"])
	; - Ресурсы
	(resources ["resource/*" "images/logo.ico"])
)
```

### Причины устройства

#### Дочерние модули

Система дочерних модулей является частью решения по созданию оптимального способа реализовывать инкапсуляцию и сокрытие для элементов модуля.
Изначально рассматривались несколько вариантов по тому, как реализовывать сокрытие, модификаторы доступа внутри членов модуля (`public` / `protected` / `private`) было решено отменить, т.к. это вызывало бы лишние проверки и мороки, при этом между членами самого модуля это несколько бессмысленно, т.к. не решает проблемы глобального доступа, а разработчик сам может поменять модификаторы внутри.
После отмены модификаторов внутри модуля рассматривались идеи о применение модификаторов межмодульного доступа (`export` / `internal`), но и это бы добавляло необходимость о проверке каждого места доступа к каждому члену модуля.
Решением было взять и проверять доступ относительно всего модуля сразу, что существенно экономило бы время.
Система дочерних модулей при этом позволяет экспортировать во-вне необходимые части закрытого родительского модуля через систему декораторов, что и стали ценой вопроса. Однако при желании можно нивелировать эту цену за счёт оптимизации встраивания (*После проверки доступа к модулю в котором определён декоратор, тупо встраивать его реализацию в месте использования, без проверок доступа внутри самой реализации декоратора, т.к. эти проверки можно выполнить предварительно при обработке модуля определяющего декоратор*). В случае же полного экспорта функционала единицы модуля предлагается использовать проверку доступа к *export-alias* (Аналогично `pub type X = Y` из Rust).

#### Определение примесей

Примеси нужны платформе `VTL` и являются её неотъемлемой частью для реализации идеи о возможности расширения и модификации платформы.
Первоначально определение примесей предполагало и определение целей для их применения, что предполагало оптимизацию взаимных зависимостей модулей за счёт явного раздела их связей. Однако в ходе рассуждений было выведено, что в таком случае в конечном итоге примеси создают "проблему разных версий классов", что заключается в присутствии в системе нескольких разновидностей одного класса, а как следствие и его экземпляра, что обязывает систему добавлять лишние проверки, будь то проверка принадлежности объекта к определённой изменённой версии класса имеющей свои особенности реализации полей / методов. Как итог разделение предела влияния примесей приносило бы больше нагрузки в последствии, кроме того и усложняло общую системную реализацию. Из-за чего было принято решение об упразднении системы до применения примесей на весь код.

#### Разрешение примесей

Идея с разрешением примесей по аналогии с *идеей дочерних модулей* появилась в попытке решения проблемы сокрытия и обеспечения безопасности в защищённых системах. Примеси нужны платформе `VTL` и являются её неотъемлемой частью для реализации идеи о возможности расширения и модификации платформы, в следствии чего отказаться от них мы не можем.
Для контроля примесей создаются специальные настройки разрешения примесей, несмотря на разрешение по умолчанию (*так сделано, т.к. в большинстве своём модули не требуют защиты от модификации и явное разрешение на модификацию сломало бы идею о возможности их свободной модификации*), для частей системы которые по каким-то причинам не должны быть модифицированы из вне эти настройки позволяют явно запретить или разрешить применение примесей.
